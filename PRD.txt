Product Requirements Document (PRD) — WhatsApp CRM Backend (Java, Spring Boot, PostgreSQL)

Style: Notion-like, developer-focused, ready for implementation in Cursor IDE
Scope (v1): Backend only — monolithic Spring Boot app with internal adapter support for multiple WhatsApp providers (primary: Meta WhatsApp Cloud API). Single-tenant (single client) but designed so provider adapters can be added later. No message-queue; bulk send will run inside app (with damage-control guidance). Auth via JWT (username/password). Deployable to AWS Free Tier using Docker + EC2 + optional RDS.

1. Objective & Goals

Primary objective: Build a production-ready backend service that:

Integrates with Meta WhatsApp Cloud API (and is architected to add other providers later via an adapter pattern).

Receives incoming messages and events via WhatsApp webhook.

Provides a CRM API (Contacts, Conversations, Campaigns, Message Templates, Message History).

Allows CSV upload for bulk sends (CSV can contain phone, name, templateId, variables, schedule time, tags).

Supports message templates (text, media, interactive buttons) and automated reply flows.

Simple user auth (JWT) with roles (Admin, Manager, Agent).

Deployed with Docker on AWS Free Tier (EC2 + RDS or container-hosting on EC2).


Template approval workflow (we’ll allow sending without Meta approval).

2. High-level Architecture

Components (single monolith JAR):

web (Controllers / REST endpoints)

service (Business logic)

integration (WhatsApp provider adapters + HTTP clients)

persistence (JPA Entities + Repositories)

dto (request/response DTOs + mappers)

security (JWT auth, filters)

util (validation, CSV parser, template engine)

jobs (scheduled tasks for scheduled sends — lightweight in-app scheduler)

Design principles:

SOLID principles, separation of concerns (Controller -> Service -> Repository).

DTOs for all controller I/O.

Adapter pattern for providers (WhatsAppProvider interface, MetaWhatsAppProvider implementation).

Clear package structure to match Cursor IDE project layout.

Use Spring Boot (latest stable), Spring Data JPA, PostgreSQL driver, Spring Security (JWT), Lombok, OpenAPI/Swagger.

Sequence (simplified):

Client calls /api/v1/campaigns or /sendMessage.

Controller validates request → Service orchestrates.

Service uses ProviderAdapter to send message to Meta Cloud API.

Response persisted to messages table and returned.

5. Database Schema (PostgreSQL)

Below are the main tables and key columns. Use UUID primary keys for portability.

Entities (DDL-style summaries)
-- users
CREATE TABLE users (
  id UUID PRIMARY KEY DEFAULT gen_random_uuid(),
  username VARCHAR(100) UNIQUE NOT NULL,
  password_hash VARCHAR(255) NOT NULL,
  role VARCHAR(20) NOT NULL, -- ADMIN / MANAGER / AGENT
  created_at timestamptz DEFAULT now()
);

-- contacts
CREATE TABLE contacts (
  id UUID PRIMARY KEY DEFAULT gen_random_uuid(),
  phone VARCHAR(20) NOT NULL,
  name VARCHAR(255),
  tags TEXT[],
  metadata JSONB,
  created_at timestamptz DEFAULT now(),
  updated_at timestamptz DEFAULT now()
);

-- templates
CREATE TABLE templates (
  id UUID PRIMARY KEY DEFAULT gen_random_uuid(),
  name VARCHAR(150) NOT NULL,
  provider_template_id VARCHAR(200), -- optional external ID
  type VARCHAR(50) NOT NULL, -- TEXT, MEDIA, INTERACTIVE
  content JSONB NOT NULL, -- structure varies by type; stores placeholders, media URLs, buttons
  created_by UUID REFERENCES users(id),
  created_at timestamptz DEFAULT now(),
  is_active boolean DEFAULT true
);

-- campaigns (bulk send jobs)
CREATE TABLE campaigns (
  id UUID PRIMARY KEY DEFAULT gen_random_uuid(),
  name VARCHAR(255) NOT NULL,
  template_id UUID REFERENCES templates(id),
  uploaded_by UUID REFERENCES users(id),
  csv_metadata JSONB, -- summary of CSV upload
  status VARCHAR(50) DEFAULT 'PENDING', -- PENDING, RUNNING, COMPLETED, FAILED
  scheduled_at timestamptz,
  created_at timestamptz DEFAULT now()
);

-- messages
CREATE TABLE messages (
  id UUID PRIMARY KEY DEFAULT gen_random_uuid(),
  campaign_id UUID REFERENCES campaigns(id),
  contact_id UUID REFERENCES contacts(id),
  provider_message_id VARCHAR(255), -- provider response id
  provider VARCHAR(50), -- META, GUPSHUP, etc
  direction VARCHAR(10) NOT NULL, -- OUTGOING / INCOMING
  status VARCHAR(50), -- SENT, DELIVERED, FAILED, READ, etc
  payload JSONB, -- original message payload sent
  response JSONB, -- provider response
  error TEXT,
  created_at timestamptz DEFAULT now()
);

-- webhook_events (incoming)
CREATE TABLE webhook_events (
  id UUID PRIMARY KEY DEFAULT gen_random_uuid(),
  provider VARCHAR(50),
  event_type VARCHAR(100),
  payload JSONB,
  processed boolean DEFAULT false,
  created_at timestamptz DEFAULT now()
);


Indexes:

contacts(phone) UNIQUE index.

messages(campaign_id), messages(contact_id) for query performance.

webhook_events(processed, created_at) for polling.

Webhook (WhatsApp Cloud)

POST /api/v1/webhooks/whatsapp

Endpoint must handle Meta Cloud webhook verification (GET for verification) and POST for events.

Sample POST payload (simplified):

{
  "object": "whatsapp_business_account",
  "entry": [
    {
      "id": "WHATSAPP_BUSINESS_ACCOUNT_ID",
      "changes": [
        {
          "value": {
            "messages": [
              {
                "from": "919812345678",
                "id": "wamid.HBgL...",
                "timestamp": "1609459200",
                "text": {"body":"Hello"},
                "type":"text"
              }
            ]
          },
          "field": "messages"
        }
      ]
    }
  ]
}


Response: 200 OK with { "status":"received" }.

Webhook handler should:

Persist event in webhook_events table.

Map to contact (create or upsert).

Persist incoming messages to messages table.

Optionally trigger auto-reply flow via TemplateService.

Expose methods:

void handleDeliveryReceipt(JsonNode payload)

Rate limits & safety

V1 will send messages sequentially per campaign. Because there is no queue, implement:

Per-campaign throttling (configurable messagesPerSecond).

Retry with exponential backoff for failed sends (max 3 attempts).

Circuit breaker pattern to stop on repeated 429/5xx returns.

11. CSV Upload & Bulk Send Flow

User uploads CSV via /campaigns/upload-csv (multipart).

Server does light validation (headers, max rows).

Parse CSV rows into campaign_recipients in-memory or temp table (for large files better to persist).

If scheduledAt present, scheduler picks campaign at that time. Otherwise either auto-start or wait for manual start.

CampaignService.start(campaignId) iterates recipients:

Map each row to Contact (upsert).

Build message payload using TemplateService.populate(template, variables).

Call WhatsAppProvider.send(...).

Persist Message with status.

Respect configured throttle.

Update campaign.status and counters.

CSV parsing

Use Apache Commons CSV to support escape characters, quoted fields.

Reject rows missing phone.

Support variables_json column to pass custom template variables.

12. Webhook Processing & Auto-Reply Flow

Webhook receives events → persisted to webhook_events.

WebhookProcessorService consumes new events:

For incoming message: map phone → contact (create if not exists).

Persist messages row for incoming.

Check autoReplyRules (simple configurable rules stored as DB entries or static):

Example: if message contains "price", reply with Price Template.

If auto-reply triggered → call WhatsAppProvider.sendTemplate(...).

Provide Admin API to manage simple AutoReplyRule entries (pattern → templateId).

13. Security & Auth

JWT-based auth with /api/v1/auth/login.

Authorization: Bearer <token> header required for all endpoints except /webhooks/** (webhook validated separately by signature or token) and /auth/login.

Passwords stored as bcrypt hashed strings.

Role-based method-level access (e.g., @PreAuthorize("hasRole('ADMIN')")).

Webhook security:

Validate X-Hub-Signature if Meta sends appsecret_proof or implement token verification (Meta supports verification by GET challenge).

14. Error Handling, Logging & Monitoring

Centralized @ControllerAdvice for REST error responses.

Use structured logging (JSON) fields: traceId, userId, campaignId.

Persist send errors in messages.error and keep response JSON for analysis.

Expose /actuator/health and /actuator/metrics for monitoring. Optionally integrate with CloudWatch.

AWS Free Tier Deployment Steps (EC2 + RDS)

Option A: EC2 (Docker) + RDS (Postgres Free Tier) — recommended for production-like separation.

Provision RDS (Postgres)

Create Amazon RDS PostgreSQL instance (db.t2.micro / free-tier) in same region.

Configure security group to allow EC2 security group or IP.

Provision EC2

Launch an EC2 instance (Amazon Linux 2 / t3.micro).

Install Docker and Docker Compose.

Transfer JAR or use Docker image from ECR. (ECR has free tier limits — can push image).

Create environment variables: SPRING_DATASOURCE_URL=jdbc:postgresql://<rds-endpoint>:5432/whatsappcrm etc.

Start container: docker run -d -p 80:8080 --env ... your-image:latest

Security group

Open port 80/443 for HTTP(S).

Restrict DB port 5432 to EC2 host.

Domain & TLS

Use Route53 or point domain to EC2 public IP. Use Let's Encrypt for TLS (certbot) — optional.

Option B: Single EC2 with local Postgres

Simpler: Run Postgres container on EC2. Only suitable for small deployments (free-tier limits).

S3 for Media

Use AWS S3 to store outgoing media (images) and their public URLs.

Configure IAM role on EC2 to upload to S3 (or use access keys).

Env & Secrets

Use AWS Secrets Manager or EC2 user-data environment or .env files — DO NOT commit secrets.

18. Operational Notes & Limitations (v1)

Rate limits: Since no queue is used, bulk sends must be throttled to avoid provider rate limits. Provide a per-provider throttleRate configuration.

Retries: Implement idempotency (dedupe keys) and retry for transient failures.

Scaling: For heavy volumes, later add SQS/RabbitMQ and worker processes or split into microservices.

Monitoring: Enable CloudWatch logs and metrics.
